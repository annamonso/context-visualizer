What it is

Multi-Agent Context Visualizer is an observability & distributed-tracing tool for fleets of AI agents running across an HPC cluster — think APM (application performance monitoring), but for many LLM agents on many nodes instead of microservices. You point it at a running ChronoLog deployment and it reconstructs how the agents actually ran — their conversations, how they delegated to one another, where time went, and what failed — entirely from ChronoLog stories, with no other backend required.

It targets the multi-agent, multi-node case specifically. It captures both each agent's LLM turns and the inter-agent calls between them; it is SLURM / cluster-aware (real node names, idle / busy state, scales to 100+ nodes); and it traces critical paths across hosts. Where a generic LLM-observability tool watches a single app, this watches a whole fleet — surfaced as the classic observability triad (traces, metrics, diagnostics) reframed for agents.

Under the hood it's a Flask (Python) backend + React (TypeScript) SPA, shipped as a standalone pip-installable plugin (a repackaging of the former clio-core/context-visualizer) with ChronoLog as the required storage substrate. Design seam: every view is a Capability served by a pluggable adapter — the app mounts only the blueprints some active adapter can serve, so a third party can add their own data source without forking.

The eight features

Every read-path tile in the diagrams below (WO · SC · IN · CL · FL · DO · TR · ME) is one of these eight — the same tabs the dashboard exposes today.

  • Workspace (Sessions) — per-conversation tree: an orchestrator + the subagents it spawned, one run replayed.
    • Pick a conversation from the dropdown.
    • Header KPIs: agents · handoffs · LLM calls · tokens · cost.
    • Scope: one selected agent, or the full workflow.
    • Sequential view — replay the run turn-by-turn on a timeline (play/pause, step, 0.5–4× speed).
    • Aggregate view — static summary graph; edge thickness = handoff frequency.
    • Interactive map + minimap; detail panel (Summary · Messages · Tools · Raw) follows the current turn.
    • Error toast when a turn fails; host mode to see every agent on one node.
  • Scenarios (Topology) — the live multi-agent graph: independent peer agents and the calls between them, grouped by scenario_id.
    • Pick a scenario from the sidebar; membership is discovered from the traffic (any agent that sent or received).
    • An edge = one inter-agent call (mcp_call · tool_invoke · direct_message), with status and latency.
    • Live mode — edges stream over SSE as calls fire; Full mode adds per-agent token/cost for finished runs.
    • KPI strip: hosts · agents · messages · tokens · errors.
    • Views: Auto, Agents (cards by host), or Hosts (grid, for 100+ nodes).
    • Replay — a playhead sweeps the scenario's time window (play/pause, 0.5–4× speed).
    • Click an agent → its Workspace; a host → host mode; an edge → call details.
    • Demo Burst fires synthetic traffic to watch the graph light up live.

    Note — a second write path to unify. Demo Burst (and any inter-agent ingest) writes directly to ChronoLog from the dashboard process, plus a local JSONL hot copy. That is a different door than the Path-A write path (spool → capture worker → ChronoLog) used by Workspace/Interactions. Two writers into the same store is one of the smears the target architecture removes by routing every writer through one EventSink port.

  • Interactions — a flat, newest-first feed of every LLM call across the whole fleet (plain list, no grouping).
    • Columns: time · provider · model · endpoint · status · stream · latency · response preview.
    • Status is color-coded (2xx ok, 4xx/5xx error) to spot failures at a glance.
    • Live / Polling indicator; refreshes every ~5s (SSE push when available, else polling).
    • Rolling window — newest 100 rows (up to 500); no search, filter, or sort in the UI.
    • Click a row → drawer with Summary · Messages · Tools · Raw; deep-linkable via ?iid=.
    • Same Path-A data as Workspace — just ungrouped: Workspace organizes it, this streams it raw.
  • Cluster — ChronoLog + SLURM topology: node-to-node traffic alongside live idle/busy state.
  • Fleet — per-node health heatmap — errors, p95 latency, throughput, cost — across 100+ nodes.
  • Doctor — ChronoDoctor: detects, clusters, and diagnoses failures, with memory that survives restarts.
  • Traces — distributed critical-path waterfall across hosts, built from inter-agent call edges.
  • Memory — per-agent working-memory view: context tokens growing and being evicted over a run.

Architecture (three layers)

  • Three layers. The frontend is a pure view layer — it fetches /api and subscribes to SSE streams, and holds no domain logic. The backend is where everything happens. ChronoLog is the durable substrate underneath it all.
  • ① Serving core is the only interface to the frontend. Flask serves the built React bundle (static SPA at /, assets under /static/workspace/), exposes the 10 per-tab blueprints under /api (plus legacy /_interceptor routes), and pushes the live tabs over SSE (/api/…/stream). The browser talks to nothing else.
  • The rest of the backend sits behind ① and above ③. ② Adapter seam turns stories into the shapes blueprints return; ④ Capture / ingest lands the write path; ⑤ Analytics engines (ChronoDoctor, Fleet, tracing, semantic) are mostly pure compute over a thin I/O layer.
  • ③ is the only door to the substrate. py_chronolog_client is imported in exactly one file (backend/chronolog/client.py); every other cluster reaches ChronoLog through its get_backend() singleton. Reads replay stories (or fall back to the drained CSV/HDF5 archive); the client speaks Mercury over two endpoints — visor portal (:5555) out, player query callback (:5557) back in.
  • Three data paths. Write (teal) — agents → capture → ③ → keepers. Read (gold) — blueprints & analytics replay stories back out through ③. Live (dashed) — the inter-agent bus fans out over SSE, bypassing ChronoLog's ~180 s keeper→grapher drain so real-time views stay instant.

Architecture target (engine behind a port · ports & adapters)

The write path, restructured so nothing above the line knows which engine stores the data. producer/ and collector/ hand events to the contract/ (the ports + event schemas); ChronoLog becomes one adapter behind it — swappable for another store, and producer/ is the clean unit a future chrono-agent absorbs, because it only ever touches the contract.

  • The one move. producer/ + collector/ depend on the contract/ (EventSink), not on ChronoLog. Every writer goes through it — no more append_event scattered across collector/, api/, fleet/.
  • Swap engines. A second store is one new adapters/<x>/ folder implementing the same contract; producer/, collector/, analytics and serve don't change. That's the "run on other engines" goal, for free.
  • Absorb later. producer/ is a clean unit — chrono-agent can take it because it only touches the contract, not the substrate.
  • Same seam for reads. The read side reads through the same contract (EventSource), and the two scattered ChronoLog spots (write client + read adapter) merge into one adapters/chronolog/.
  • Offline & tests for free. Point the contract at adapters/local/ (JSONL) and the app runs with zero ChronoLog — which is what offline mode fakes by hand today.

The move: producer/ (was emit) is the agent-side producer library — dependency-free, ships into agents, the exact unit a future chrono-agent absorbs. collector/ (was capture) is the server-side intake. contract/ is the shared agreement everyone depends on — the event schemas (nouns) plus the ports (verbs: sink · source · bus), pure and zero-dependency. Today's collector/ dissolves: the emit helper → producer/, the daemon → collector/streaming.py.

This mirrors OpenTelemetry: producer = instrumentation / SDK, collector = the OTel Collector (receive → buffer → export), adapters/<engine> = the backend it exports to. A well-worn shape for exactly this problem.

One-way dependencies: everything depends on contract/; contract/ depends on nothing. producer → contract · collector → contract · adapters implement contract's ports. So producer sits at the edge importing only the contract — which is what lets it graduate to its own package.

The read side (⑤). One vertical slice per feature — and a feature is exactly one capability = one tab = one frontend page (the SPA already has eight matching *Page.tsx files). The old analytics modules were never features; they dissolve into the slices they serve: fleet/ → fleet, diagnostics/ → doctor, analysis/ splits into traces + memory. Each feature's logic is read.py (pull via EventSource) · compute.py (pure, unit-testable) · view.py (view-model); its HTTP blueprint stays in the api/ serve layer and calls into it (a controller↔service split). Reads that need raw events go through the same contract.EventSource the write side writes to — which removes the last feature→feature imports (analysis→fleet, fleet→diagnostics).

Still open — now product, not structure: semantic/ + checkpointing/ are one headless feature (checks + rollback, no tab, and checkpoints are never created in the running system today) — either finish it (add a tab + wire checkpoint creation into the write path) or park it as experimental and self-contained. Separately: whether the Capability gate stays fused with data-access or splits from it.

The data

This project collects agent-activity data so we can see how a fleet of AI agents actually behaved — what each one did, how they worked together, where time and cost went, and what broke — long after the run is over.

How the agent works

An agent is an LLM given a goal and the tools to pursue it — it decides its own next steps instead of following a fixed script.

Concretely, it runs a think → act → observe loop that repeats until its task is done — the core cycle at a glance:

Step by step:

  1. Start. It's spawned on a node with a role and a goal — often because a parent agent delegated the work to it.
  2. Think — the LLM call. It sends its context (instructions + history + task) to a model, which replies with its reasoning plus either an action to take or a final answer. The reasoning is the model's output — not a separate step.
  3. Act. If the model asked for an action, it runs a tool (read a file, run code, search) or delegates to another agent via an inter-agent call.
  4. Observe. The action's result is appended back into its context — working memory grows; it may retrieve more or compact / evict to stay within budget.
  5. Loop. Back to Think with the new observation, repeating until the model returns a final answer.
  6. Finish. It returns its output; any subagents wrap up.

Errors & recovery are cross-cutting — a retry or a checkpoint-backtrack can happen at any step, not as a stage of its own.

The produced data

Each pass through that loop throws off data. Here it is — mapped to the step that produces it:

Loop stepAgent produces…What it's for
ThinkLLM call — prompt, response & reasoning, model, tokens, cost, latencycost / speed / quality, prompt debugging, why it acted
ActTool use — files, web, code, MCP calls + their resultsside effects, what it touched
ActInter-agent message — delegation & handoffs to other agentsthe coordination graph, bottlenecks
ObserveContext / working memory — window contents; growth, retrieval, evictionmemory pressure, lost-context bugs
any stepErrors & recovery — failures, retries, backtracks, restoresreliability, debugging failures

Data sources

None of this data exists until the agent produces it — there is no external log to scrape. Each signal is emitted at a specific point in the agent's run, and you access it by instrumenting that point — a thin shim around the agent that captures the event as it happens.

SignalProduced when…Accessed by…
LLM callthe agent calls the modelwrapping the model client — the request + response
Tool usethe agent invokes a toolhooking the tool-dispatch layer — name, args, result
Inter-agent messagethe agent delegates to a peerintercepting the delegation / MCP call boundary
Context / memorythe agent assembles its context windowreading the framework's context state each turn
Errors / recoverya step fails, retries, or backtrackshooking the error / retry handler
Lifecyclethe agent starts, finishes, or spawns a subagentthe runtime's lifecycle callbacks

The pattern is the same everywhere — a boundary inside the agent's run, tapped by a bit of instrumentation. No instrumentation, no data: an un-instrumented agent is invisible, and none of this can be recovered from the outside after the fact.

Of everything above, this tool collects a curated slice — the Data model below is exactly which of it we keep, why, and how.

Data model

Everything is stored as time-ordered JSON events in ChronoLog, grouped into chronicles (one per data type) and keyed per agent session or scenario. Two capture paths produce four core record types:

RecordPathCapturesChronicle
LLM interaction Path-A one agent turn — prompt, response, model, tokens, cost, latency llm_interactions
Context node Path-A a working-memory change — op (add / evict), node, token size context_graphs
Recovery event Path-A a backtrack / checkpoint restore recovery_events
Inter-agent edge Path-B one agent→agent call — caller, callee, correlation id, start / done, duration ia_<scenario>

Everything the dashboard shows is reconstructed from these four. Anything else is derived, not collected — Fleet rollups (metrics_rollup) and Doctor incidents are computed on top; checkpoints and __index__ are housekeeping.
